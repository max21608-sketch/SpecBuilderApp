**What it deliberately leaves out of the gates** (still on the checklist, as
"also outstanding"):
- COM 1–3, stitching, studs and interliner. They matter on the rare cabinet
  with an upholstered or leather-lined part, and blocking every table on them
  is what produced the 30-question side table.
- Floor type, fabric quantities, "needs split?" (the site access row covers
  it), image reference, visible fixings, felt.

**What this does to the test tender.** A side table goes from 30 blocking
questions to its own four basics (dimensions, indoor/outdoor, stone, glass)
plus what the project answers once.

**Known weak points, for whoever checks it:**
- DT is not asked about lighting (103), yet row 120 offers wire access to a
  dining table. Boardroom tables do have power. If that matters, add DT
  to 103.
- "Fitted" (104) is not asked of sideboards or consoles, which are sometimes
  wall-hung.
- Rows 112 and 113 are one field at one gate with two rules; the seed may
  need them as one row with a per-type condition.
- No row is tied to an item's level. His matrix does not do that either.

**Label it everywhere it shows.** Wherever a cabinetry gate view or TGQ count
comes from these rows, the screen says "provisional cabinetry gate model,
drafted by AI on 20 Nov 2026, not yet confirmed by Matthew". Every seeded
row's `notes` says the same.

## B. Swivel on sofas — BEST GUESS

**Decision.** In a cheat sheet that covers more than one of his types, the
app suggests which type each item is from its name, a person accepts it, and
"Swivel mechanism" is asked only of armchairs (A) and bar stools (BS), as his
row 12 says. The first cut of the rule:

| The item's name contains | Suggested type |
|---|---|
| sofa, settee, loveseat | S |
| bench, stool (not bar or counter stool) | B |
| daybed, chaise | D |
| anything else in "Armchairs Benches Stools Sofas" | A |

It is a suggestion like the category and the level: shown with its reason,
never written unseen. An item nobody has typed keeps today's behaviour, so
nothing is silently un-asked.

**Why this and not "never block on swivel":** an armchair's swivel base does
change the price, which is why it is in his TGQ.

## E. Questions worded for us

**Decision.** A question worded for BW is In-house and is never sent. The
client is shown the question only, never the BWS field name beside it.

In-house by wording, on top of D:
- Project sold with metal finish or metal paint effect?
- Needs split? Where?
- BW Standard felt or COM/BOM?
- Has the client provided details (heights, SH, etc.) of the chairs?
- Has the client provided details (heights, top thickness, base design) of
  the tables?
- The client is expecting exact copy from their drawing or there is
  possibility of suggestion BW standards?
- Has client been advised of BW Standards?
- Make client aware of BW standard lid stays
- Is it sitting alongside sofa's tables BW need to be aware of?
- Fabric quantities
- Image / Drawing / Repeat Reference

Where the client does need to be asked the thing behind one of these (the
metal finish itself, say), the field's own question carries it: "Metal
finish 1".

## F. "COM" for fabric BW supplies

**Decision.** Screens say "Fabric 1", "Fabric 2", "Fabric 3", with the BWS
field name beside it in small type ("BWS: COM 1"). The quote lines print
"FABRIC:" unless the fabric is marked as the customer's own material, and
then "COM:".

**What it needs that does not exist:** a way to mark a fabric as COM. That is
one tick on the finishes library row, off by default. The BWS file is
unchanged; its column is called COM 1 and stays that.

| Decision | As recorded above | As built, and why |
|---|---|---|
| A | Rows 106–110 and 112/113 as separate rows beside his | The table's uniqueness rule refused them. The rule is now a trigger that refuses two rows for one field at one gate only where one cheat sheet could receive both (`spec_field_gates_identity_overlap`). His 35 rows are untouched: "All categories" reaches the new types through a generated column, not an edit |
| A | 103 (lighting or power) not asked of dining tables | **Asked of all eight.** Row 120 depends on it, so a dining table could never have cleared TG0 |
| A | Substrate, runners, hinges "palette + free text" | **Free text.** The app holds no palette for them, and none was invented |
| A | — | **77 checklist questions added** to the cabinetry sheets, because the gate rows had no question to be answered through. The four yes/no questions are new rows beside the sheets' older wording |
| A | — | **Existing items need a backfill** (`db:backfill-question-rows`): a seed that adds questions creates no answer rows on items already categorised. The first answer now creates the row too |
| C | "Interliner required?" once per project | **Stays per item.** Six cabinetry sheets ask it; one press would have written an interliner onto tables and wardrobes |
| C | Area answers as a third kind of count | They stay in the item's own count; the area card is the project-wide card one level down, and it names its phases and follows the phase filter |

| D | Only client questions in a chase | Only for a designer or client recipient. A colleague can still be sent anything |
| D | "Ask the client" on any question | **CAM questions only.** An in-house question is refused in words |
| D | — | A designer's draft made earlier that holds a question now ours is flagged on its card with Remove beside each; it still opens and downloads |
| E | "Project sold with metal finish…" in-house | **Stays a client question with a client wording** ("Metal finish 1, and where on the item"). It is the only question for that BWS field on all 17 sheets; in-house would have removed metal finish from every chase |
| E | — | COM 1/2/3 and Timber finish 1 get client wordings too ("Fabric 1"…) |
| F | COM by a tick on the library row | The tick exists (`customer_supplied`), takes a reason, and COM goes by the fabric's **code**, linked or not. A fabric with a BW standard in force is always FABRIC |
| G | Five label links | **Two seeded** (Swivel, Studs / nailing). "Seat build" was seeded and then removed in review: "Seat & back build" landed on the seat alone. Back cushions and Stitching were not seeded: the first would catch a fabric callout, the second already lands |

### Rollout — the order matters

1. **Migrate** (`0061`, `0062`, and the intake build's `0065`). Additive; the
   old code keeps working against them.
2. **Deploy** the code. Between this and step 3 the app behaves as it did:
   audiences default from the old rule and no cabinetry model exists.
3. **Seed** (`0014`–`0016`, with the rest; idempotent). The cabinetry model,
   the audiences and the two aliases arrive, labelled provisional.
4. **Backfill** `db:backfill-question-rows`: dry run first, then `--apply`.
   Existing items get their new question rows.

A seed before the deploy would show the AI model with no label. New code on a
database without the migrations fails every chase, fill-in and record read.
