## Step 1 — bills: every column recorded, never refused (Coder A, ~1.5 days)

Everything a person or a model does here lands on the **staged document**, so the review screen stays the human gate. **Nothing in this step calls a model.**

1. **Staged BOQ v4** (`src/lib/boq-import.ts`, `BOQ_SCHEMA_VERSION = 4`, v3 still readable). Each sheet records:
   - `columns`: role → `{ index, heading }`;
   - `headerRow` / `headerRows`;
   - `mappingSource`: `synonym | layout | model | person`, plus the layout name.
   - Today's staged sheet does not record where a role came from, so a wrong column is invisible.
2. **The roles grow, and a column can be ignored on purpose.**
   - Existing roles: code, item description, qty, unit, area, designer, category, product reference.
   - New role: `subArea`. Default: area is composed as `<Area> / <Sub-Area>` verbatim and shown on the review. **This is Max's to confirm; see Questions.**
   - New role: `sourceLine` ("Line", "Item No"), kept as the line's own number.
   - New role: `notes` / remarks, kept on the line and written to `internal_notes`.
   - Explicit `ignore`, for price, image and cost columns. **Prices are never read**; the rule that this app holds no pricing stands.
   - Fix the known gap: `qtyUnit` is staged and never written.
3. **The synonym list becomes seed data**, as CLAUDE.md already asks. `boq_column_aliases (role, term_norm unique)` holds today's `COLUMNS`, reproduced exactly.
   - A test asserts the seeded list equals the old constant on day one, so nothing that reads today changes.
   - It is still a WHOLE-heading match after folding case and whitespace, never a substring. With substrings, "Category Code" would become the code column and "Unit Price" the unit column.
4. **Layouts** (`boq_layouts`, 0040). A layout is:
   - a name ("Aman Interiors — AMB pricing document");
   - the ordered list of folded headings it was saved from;
   - role → heading.
   - It matches a sheet only when every mapped heading is present exactly.
   - Order of precedence: layout, then synonyms, then (Step 2) the model's suggestion, then a person.
   - Saving a layout is a person's tick at confirm ("Remember these columns for this specifier's bills"), and it writes under a change-set-free admin row with `created_by`. This is how "nail the major specifiers" becomes data, not code.
5. **A bill with no recognisable header is NOT `failed`.** It parses to `parsed`, with each unmapped sheet in a `needs_columns` state. The review screen opens on a **Columns panel**:
   - The first ~25 rows are shown as a grid, using the existing table primitives.
   - Click a row to make it the header, or two rows for a split header.
   - Each column gets a role select, with the reader's current guess pre-filled and badged by source.
   - **Read the bill with these columns** re-parses from the stored source (`attachments`, free, no model) through a new `POST /api/imports/[id]/columns`, fenced on the run's version.
   - The lines table appears underneath and nothing is confirmed.
   - **Change columns** is offered on every bill, including one the synonyms read, because a wrong match is correctable only if it is visible.
6. **Try again is fixed for bills.** On a failed or unmapped bill, the Documents tab and the pack screen say **Set the columns** and link to the panel. `retryAllFailed` skips bills. A bill uploaded without a preserved source says so, and asks for the file again rather than offering a re-read that cannot happen.
7. **The refusal sentence stays as the panel's heading text**, rewritten to point at the controls under it.

**Trap avoided:** a remembered layout that silently applies to a bill whose columns moved. That is why the match is exact on every mapped heading, and the panel shows the grid for any bill read by a layout, until the reviewer closes it once.

## Step 2 — bills: the model reads the structure, code reads the cells (Coder A, ~1 day)

1. **When layout and synonyms both fail on a sheet, one structure read runs automatically.** It happens when the review screen first opens a `needs_columns` sheet, through `POST /api/imports/[id]/suggest-columns`.
   - Model: `EXTRACTION_MODEL`, effort `medium`, `maxDuration` 120, forced tool. This follows `document-classify.ts`' pattern: a closed schema, `zod` with `.catch()`, and document text treated as untrusted.
   - Input: the first ~40 rows of each sheet (`spreadsheetSheetsToText`), plus every distinct heading.
   - The tool returns:
     - the header row(s);
     - per column: a role from the CLOSED list or `null`, with the heading it read as evidence;
     - `rowKinds` for sample rows (`item | section | subtotal | blank`), with the pattern it saw.
   - The upload row states the charge beforehand: "a bill in a layout the app does not know costs one small read".
2. **Code validates, then applies it to staging.** Validation checks: a role only once, columns that exist, and a code or description column present. The reviewer then sees:
   - lines already staged;
   - a yellow banner, "Columns read by the model — check them", with its evidence per column;
   - the Columns panel open.
   - **Confirm requires "Columns checked"** whenever the source is `model`. The model never types a value, so a quantity cannot be mis-copied.
3. **Section and subtotal rows** close the logged defect "a subtotal row becomes a record". Every staged line gets a `rowKind`:
   - A row with a description, no code and no quantity is a `section`.
   - A row the model or a person marked `subtotal` is a `subtotal`.
   - Both default to Ignore, flagged, and one click brings a row back.
   - "Take the area from section headings", for a bill with no area column, is an OPTION on the panel, set by the reviewer or proposed by the model with its evidence. It is never automatic.
4. **Measurement tool `npm run boq:gap -- <folder>`**, read only. For each file and sheet it prints:
   - how the header was found;
   - the column map;
   - line count, lines with no code, lines with no qty;
   - suspected section and subtotal rows;
   - qty sum.
   - `--golden <dir>` compares against a hand-checked expectation per bill, kept OUTSIDE the repo in `~/dev/localstack/boq-golden/`: line count, every code, and every quantity. The output is a per-file accuracy figure.

**Trap avoided:** a model transcribing 300 quantities, where one wrong digit is a wrong order and nothing questions it.

**DoD:**
- The AMB bill, with no layout saved, reads with the model's columns. The banner and the evidence are shown.
- `boq:gap --golden` reports 100% lines, codes and quantities on it.
- A synthetic bill with a section row and a subtotal shows both as suggested Ignore.
- Calls logged.

## Step 5 — configurations numbered under their line, and a line that shows its common specs (Coder C, ~1.5 days)

1. **Numbering (0039).** `spec_records.variant_ordinal int`, allocated `max+1` per parent under the parent lock, never reused, and backfilled in `naturalConfigurationOrder`. So S-301 TYPE 1–5 become **12.1–12.5**.
   - `record_no` stays the project-wide surrogate.
   - ONE `recordLabel()` helper (`src/lib/chase-drafts.ts:145`, moved to a leaf) renders `12.1` / `P18181-012.1` and replaces the inlined templates in: `SpecTable`, the record title, chase, infill, the check sheet, the export's Specs sheet, the quote and costing sheets, and history.
   - Exports sort by `(coalesce(parent.record_no, record_no), variant_ordinal)`, so a configuration sits under its line, not at the file's end. Row order does not change what an import replaces.
   - Old snapshots keep the label they were taken with: history is history.
2. **The bill line's Specs tab** (`src/app/dashboard/records/[id]/page.tsx`), for a line with active configurations:
   - **Common to all 5.** A pure `configuration-common.ts` groups the siblings' active attributes by slot, then BWS field, then label. A row is common when every configuration holds the same value, unit and state. Otherwise it is **Differs**, with each configuration's value.
   - Below it, a **tab per configuration**, in natural order, the same layout every time: dimensions, then fabrics and finishes, then notes. Each tab shows that configuration's own specs, with **Open 12.3** linking to its full record.
   - The existing configurations card, *Add a configuration*, rename and retire all stay.
   - The line's own pre-split specs, which are not exported, fold into one closed "On the bill line itself — not exported" section.
3. **An edit to a common row fans out.**
   - New route `POST /api/records/[id]/common`, ops `correct | add | retire`. It carries every sibling attribute id and version the screen showed, and refuses the whole request if the configuration set or any version changed. Partial writes are not possible.
   - One change set, one version per configuration.
   - `correctAttribute`, `createAttribute` and `retireAttribute` gain the `changeSetId` / `snapshot:false` parameters that `editAnswer` already has.
   - **The Checklist tab** does the same for answers identical across configurations (Access is the proof), reusing `answers/apply`'s machinery.
4. **Gates and TGQ are untouched.** Each configuration still carries its own full copy, so every loader stays as it is. That is the reason fan-out was chosen over inheritance.

**Trap avoided:** a "common" edit that overwrites a configuration somebody deliberately changed. A differing row is never editable as common; it shows each value instead.

## Step 6 — BW standard beside the client's words (Coder D, ~1.5 days)

1. **0041 on `record_attributes`:**
   - `standard_value text`, `standard_option_id` (FK to `spec_palette_options`, nullable);
   - `standard_state` (`proposed | agreed | tbc`);
   - `standard_set_by` / `_at`;
   - a CHECK that a state exists only with a value, or is `tbc`.
   - `value` goes back to meaning what the DOCUMENT said, always.
2. **Intake.** `PaletteChoice` stops writing `value`. It sets the observation's `standard` (option or TBC) beside the untouched wording, and `confirm-drawings.ts` writes both. The row reads "Client: feet dark tinted wood… · BW standard: BW Oak Grey – Open grain 10% (proposed)".
3. **After confirm**, on the record's Specs tab and the infill screen:
   - **Set BW standard** and **Client agreed**, each through a change set and a version, with evidence attachable (the client's "yes, fine" email);
   - `correctAttribute` carries the standard forward.
4. **What ships.** `renderAttributeValue` (`src/lib/bws-export.ts`) is the single composer:
   - the export, the quote and the costing sheet ship the standard when one is set, and the client's words otherwise;
   - the **check sheet shows both, in separate columns**;
   - the checklist answer follows the same composer.
   - **Default, to confirm:** a `proposed` standard makes the answer `tbc`, "awaiting client agreement". So the chase can ask "Can you accept BW Oak Grey 25% for the 30% oak specified?", and an `agreed` one settles it.
5. **Backfill, `npm run db:backfill-standards`.** Dry run unless `--apply`, safe to re-run, same guards as the other backfills. For confirmed attributes whose staged observation had `valueRaw ≠ value` and whose value is a palette option, it restores the client's words to `value` and moves the option to `standard_value` (`proposed`). The words were never lost from `intake_runs.parsed`. Run on the local stack; on the sandbox only by Max.

**Trap avoided:** a single field that switches meaning between "what the client said" and "what we will make". That is today's defect, and it is exactly what the check sheet exists to catch.

**DoD:**

- Press Client agreed with an `.eml`.
- The export cell reads the standard; the check sheet shows both; the history shows the proposal and the agreement.

## Step 8 — Matthew's specifier bills (when they arrive; the loop runs per specifier)
