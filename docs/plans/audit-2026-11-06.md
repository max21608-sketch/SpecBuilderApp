# The whole-codebase audit (2026-11-06), and the plan that follows it

Max, 2026-11-06: *"go through the entire code base, meticulously. Look for
issues. Look for things that aren't really working at the moment. Or issues
that might arise in the future. And just generally audit the code. Suggest and
plan ways that it could be improved."* And, mid-way: *"include in this the
stuff we mentioned in project next steps."*

**Status: AUDIT AND PLAN ONLY. Nothing here is fixed.** Every line number is
on `staging` at `2cb4630`. Nothing was run: no tests, no build, no database,
no model call. "Confirmed" below means the code path was read end to end,
twice: once by the auditor for that area and once more by the session that
wrote this, in the source, before it was allowed into §2 or the plan.
"Plausible" means it was traced but depends on a timing, a deployment setting
or an SDK internal nobody read.

**How it was done.** Eight read-only auditors, one per area, each told what
`found-in-use.md`, `spec-change-audit-2026-10-23.md` and the README's "Still
open" parts already record so that the effort went into what is NOT recorded.
Their reports were cross-checked against each other (two found the revised-bill
defect independently, from different ends) and the consequential ones re-read
in the source. The areas: the authorisation boundary and all 84 routes; the
database layer (49 migrations, 13 seeds, the runners and backfills); the bill
intake pipeline; the model-read and drawings pipeline; everything that changes a
spec after intake, plus email; everything downstream of a confirmed record
(gates, TGQ, chase, the four exports, the overview's numbers); the screens; and
tests, tooling, operations, dependencies and documentation drift.

**What this is not.** It is not human acceptance of anything, and it found no
evidence either way about what Matthew and Claudia hit on pilot this week. It
is also not exhaustive on the lows: each auditor was asked to spend its effort
on what matters, so a clean "low" list means little was found, not that nothing
exists.

## 1. The short version

Twelve things, in the order they would hurt. Each is confirmed in the source
unless marked otherwise.

1. **The checklist freezes against the bill.** `applyAnswerFills` and
   `applyAnswerRetractions` recognise only an answer a SHOP-DRAWINGS run wrote.
   Since 2026-09-30 the bill is the main source of finishes and sizes, and its
   confirm recomposes answers with the BILL run as source, which is neither
   shop drawings nor null. From then on no correction, no finish edit, no BW
   standard, no "use the drawing's over the bill's" and no retire can touch
   that answer. A retired bill fabric still ships in the BWS file, because the
   export falls through to the answer when no attribute holds the field. §2.E1.
2. **A revised bill retires every configuration on the phase.** A configuration
   carries no bill code, so no line pairs with it, so the retire step sweeps
   it. Revise a phase holding S-301 TYPE 1–5 and the five jobs are gone from the
   export; the bare parent ships instead. Found by two auditors independently.
   §2.C1.
3. **The quantity reader invents 0 and joins digits.** `Number("")` is 0, so
   `TBC`, `N/A`, `As req'd` become quantity 0, never "not given"; stripping
   non-digits turns `2 x 3` into 23 and `12 (6+6)` into 1266; a fractional
   quantity (`1.5`, `3.6 m`) reaches an integer column and fails the whole
   confirm with "Nothing was written". §2.C2, C3.
4. **A comma is always a decimal point.** `W1,200 x D600 x H750mm` composes
   `W1 x D600 x H750mm` with no flag, in the bill reader and the drawings reader
   alike. §2.C4.
5. **A timed-out read is billed up to four times.** Our own 740 s deadline
   throws an abort the model wrapper classifies as a retryable transport error,
   so the queue redelivers and each delivery runs the full read again. §2.D1.
6. **An email taken off the wrong project can never be put on the right one.**
   The replay key is the message alone, so the second assign finds project A's
   run, links it, and never sets the project. The screen says OK; nothing is
   read. This is the only remedy the auto-assign gate promises. §2.A1.
7. **A stale "replace" tick retires a value into a note.** The acknowledgement
   is keyed on the record only; move the row to a note or another slot after
   ticking, and the confirm still retires the bill's width, superseded by a
   note. §2.D2.
8. **A second edit inside an open change writes no new version.** The snapshot
   insert is `on conflict (record_id, change_set_id) do nothing`, written for one
   transaction, applied across the many an open change spans. The version holds
   the first edit only and later ones are credited to the next change. §2.B1.
9. **Confirm sends the version from before the save it just waited for.** On
   the drawings card and the spec-document review the versions come from the
   click's render, so typing a correction and pressing Confirm within a second
   reads "edited in another tab. Reload" with nobody else in the document.
   §2.G1.
10. **A swatch is served inline as whatever content type the uploader
    declared** — a stored script on the app origin for any editor. §2.A2.
11. **`npm run db:backfill-answers` is stale and would corrupt answers if run.**
    It predates qualifiers, the finishes library and BW standards, and writes
    outside any change set. CLAUDE.md still lists it as safe to re-run. §2.B2.
12. **CI proves none of the database tier.** Every confirm path, the export
    scope, the coverage assertion and every CHECK guard skip behind green on
    every push. §2.H1.

Also confirmed and consequential but one step further down: a round item can
never satisfy TGQ (F3); the chase screen blocks level-less records that
Matthew's matrix does not need a level for (F1); a category change on a record
that has ever been chased is a bare 500 (B3); a configuration's note merge
ignores which configuration a note belongs to (D5); the drawings confirm bumps
`spec_records.version` through `level_suggested`, staling unsent drafts (D4);
chase drafts can include another project's questions (A3); there is no error
boundary anywhere, so one bad staged row takes out the whole dashboard (G4).

## 2. Findings by area

Severity: **C** critical, **H** high, **M** medium, **L** low. Each entry: what
is wrong, the failure, the fix in a sentence. "Already known" items were not
re-reported; see §2.X at the end of each area where they matter.

### A. The authorisation boundary and the routes

Clean: every non-public route calls `getSessionUser`; the upload token is
project-scoped, private, type-allowlisted and capped; the Graph webhook's
`clientState` is hashed and compared in constant time; all four exports 400 on
an unknown parameter; the `.eml` routes are attachment + nosniff; the chase
HTML is escaped; the other two-id routes scope the sub-id to the project.
`next` is locked at 15.5.25, past the 2025 middleware-bypass advisory.

- **A1 (H, confirmed). An unassigned email cannot be re-assigned.**
  `src/lib/email-registration.ts:182-207` and `:364-410`. `unassignMessage`
  nulls `intake_run_id` but keeps the run with
  `registration_request_id = email:<id>` (globally unique) and never clears
  `mime_attachment_id`. The next assign finds that run, writes only
  `intake_run_id`, returns 200 and never sets `project_id`,
  `routing_status` or `assignment_kind`. Even with a new run, the `.eml` copy
  sits under `projects/A/`, which B's read is refused. Fix: key the replay on
  message AND project (`email:<id>:<projectId>`), clear
  `mime_attachment_id` on unassign, re-copy the MIME. Test gap: the db test
  covers unassign, never re-assign.
- **A2 (M, confirmed; scenario depends on the upload allowlist). Swatch XSS.**
  `src/app/api/finishes/[id]/swatch/route.ts:67,126` stores the client's
  `contentType` verbatim; `:46-47` serves it `inline`. `nosniff` does not help
  when the declared type is `text/html`. Fix: take the type from
  `headTrustedBlob` and refuse anything outside `image/png|jpeg|gif`, as
  `patchLinePicture` already does.
- **A3 (M, confirmed). Chase drafts can carry another project's questions.**
  `src/app/api/drafts/generate/route.ts:185-238`, `edit/route.ts:152-215`,
  `src/lib/chase-drafts.ts:779-860`. `loadQuestionsByKey` selects
  `r.project_id` and neither route compares it; its `join requirements q on
  q.id = any(...)` is a cross join with no `q.category_id = r.category_id`,
  so any requirement pairs with any record and reads as `missing`. Fix:
  refuse `question.projectId !== input.projectId`; require the category join
  (and the split-heading and active-run predicates, which are also absent).
- **A4 (M, confirmed for the code; plausible for the environment). Sessions
  cannot be revoked.** `src/lib/auth.ts:20-27`, `middleware.ts:57-70`,
  `session.ts`, `auth/logout`. Role and `active` live in a 7-day JWT; logout
  deletes the cookie only; no `aud`/`iss`/environment claim, so if
  `AUTH_SECRET` is shared a staging token is valid on pilot. Fix: `aud =
  APP_ENV`, a `token_version` checked in `getSessionUser`, a shorter life.
- **A5 (M, confirmed). No spend cap on charged reads.** The cap is 3 in flight
  per pack (`extraction-slots.ts:80-155`), never a count. Every new batch gets
  three more; once Graph ingestion is on, every message that reaches the inbox
  in To/Cc is read at Opus 5.5 high. CLAUDE.md's "counts against the
  per-project cap" describes a cap that does not exist. Fix: a per-project,
  per-day count of opened attempts; over it, hold for a person.
- **A6 (M, confirmed). Any non-Latin-1 filename breaks the byte-serving
  routes.** `imports/[id]/source/route.ts:61-65` (502),
  `attachments/[index]/route.ts:98-114` (unhandled 500),
  `change-sets/[id]/evidence/route.ts:31-38`. `Headers` needs a ByteString, so
  a curly apostrophe or en dash in `Ronnie Scott’s – Drawings.pdf` throws.
  Every "page N" provenance link on such a document is dead. Fix: one helper
  emitting `filename="<ascii>"; filename*=UTF-8''<encoded>`.
- **A7 (M, plausible). Percent-encoded dot segments may beat the project
  prefix check.** `blob-source.ts:69-78` refuses a literal `..` but not
  `%2e%2e`. Whether the SDK re-encodes was not checked. Fix: refuse `%`, and
  allow only `^projects/<uuid>/[A-Za-z0-9._ ()/-]+$`.
- **A8 (M, confirmed). Header spoofing can trigger an automatic charged
  read.** `email-routing.ts:73-80,135-145`. `forwarded_from_inbox` reads
  `Resent-*`, `X-Original-To`, `Delivered-To`, `X-Forwarded-To`, which any
  external sender can set (Exchange strips only `X-MS-Exchange-Organization-*`);
  `recipient_is_inbox` reads To/Cc, which a Bcc delivery can set freely. Both
  are auto-assign signals. Latent while Graph is disabled. Fix: trust only the
  Exchange-stamped family or Graph's reported transport recipient, and put A5's
  cap in front of it; add both to `docs/integration.md`'s activation list.
- **A9 (L). No security headers** (`next.config.ts`): no CSP, no
  `frame-ancestors`, no referrer policy, on an app serving NDA documents
  inline. Clickjacking a reviewer onto Confirm is possible today.
- **A10 (L).** The source route (`imports/[id]/source`) has no `nosniff` and
  serves an `email` run's `.eml` inline, which CLAUDE.md says never happens.
- **A11 (L).** Login has no throttle and its timing says whether an account
  exists (`auth-node.ts:46-54` returns before scrypt for an unknown email).
- **A12 (L).** Error details leak on pilot and staging: `login/route.ts:39-53`
  appends the driver message whenever not production; `uploads/token:66-68`
  and `imports/route.ts:719-722` return raw exception text.
- **A13 (L).** The matcher's exclusions are prefixes (`middleware.ts:117`,
  comment at `:99-102` claims "EXACTLY this path"): a future `/api/cronjobs`
  or `/api/graph/notifications-admin` is public. Fix: anchor with `(?:/|$)`.
  And route handlers never check the role, so writer authorisation exists only
  in the matcher.
- **A14 (L).** Cron secrets compared with `===` (three routes); the Graph
  validation token reflected without `nosniff`.
- **A15 (L).** Evidence and swatch pathnames are never HEADed, so a change set
  can carry "evidence" pointing at nothing, with a client-supplied size and
  type.
- **A16 (L).** Retiring a phase (`runs/[runId]`) and setting a level take no
  version; retiring a preamble note needs no reason and opens no change set
  (known since 2026-10-23); 35 of 64 dynamic routes never validate the path id
  as a UUID, so `abc` is a non-JSON 500; `projects` POST is check-then-insert.
- **A17 (L, confirmed). CSV formula injection.** `bws-export.ts:666-669`
  quotes but never neutralises a cell starting with `= + - @`; cell text comes
  from client documents. The xlsx paths are safe. Fix: prefix `'` on the three
  human-read CSVs; decide deliberately for the BWS one.

**Measured:** 58 route files export a write handler; 6 parse the body with no
schema (`projects` POST, `uploads/token`, the multipart BOQ path, `answers/[id]`
with no length limits, two that take no body). 26 of 84 route files have no
catch, so a driver error is a non-JSON 500. Five different filename sanitisers.

### B. The database layer

Clean: every CHECK re-listing is the union of the values before it (the 0028
loss is the only one, and 0032 restored it); every TOE date read uses `::text`;
no string-built SQL; no backtick in a `sql` template; all 21 lib files that
write spec content do so inside `withTransaction` with a change set, except
B2; `REASON_REQUIRED_KINDS` and `CHANGE_SET_KINDS` match 0046's live CHECKs.

- **B1 (H, confirmed). A later edit inside an open change takes no version.**
  `record-snapshot.ts:120` (`on conflict (record_id, change_set_id) do
  nothing`), reached through `changeSetForEdit` (`change-sets.ts:243`), which
  attaches every later edit to the actor's open change. The clause was written
  for one transaction touching a record twice; an open change spans many. The
  version holds the first edit; the diff shows W only; D appears in the NEXT
  change's diff under that change's reason and evidence; a baseline in between
  records a state the record never had. Fix: when the change is open, a new
  snapshot per transaction (or re-snapshot the change's records on close).
  Note this was the infill DoD's intent ("one version per record"), so the fix
  is a design change to agree with Max: one version per change set per record
  is only right if it is taken at the END.
- **B2 (H, confirmed). `db:backfill-answers` is stale.**
  `db/backfill-answers.ts:124-137` selects no `qualifier`, `finish` or
  `standard`, writes with no change set and no snapshot, and rewrites identical
  values (bumping answer versions). A re-run overwrites the library's words
  with the drawing's raw text, drops qualifiers and standards, and confirms an
  answer over a TBC finish. Fix: retire the script and remove it from CLAUDE.md
  and `db/README.md`, or rebuild it on `recomposeAnswers` + `snapshotRecords`.
- **B3 (M, confirmed). A record ever chased cannot change category.**
  `record-category.ts:78` deletes its `missing` answers;
  `email_draft_items.answer_id` is `on delete restrict` (0005:231) and coverage
  rows reference exactly those answers. 23503 → "Nothing was written".
  Fix: refuse in words, or retire rather than delete (`coverageStaleReasons`
  already handles `answerRemoved`).
- **B4 (M, confirmed). The audit trigger copies whole documents, email bodies
  and password hashes into an undeletable table.** 0002:307 audits
  `intake_runs` with `parsed` and `raw_response`; 0021 audits `email_messages`
  with `body_text`; 0001:222 audits `users` with `password_hash`. Every review
  autosave writes two copies of the staged JSON (hundreds of KB per click on
  the AMB read). It defeats any retention decision and is the likely cause of
  "the sandbox database is full". Fix: drop the trigger on `intake_runs`, or a
  `write_audit` variant that excludes named columns.
- **B5 (M, confirmed; last bullet plausible). A project cannot be deleted.**
  `email_messages.project_id on delete set null` (0021:101) conflicts with
  `email_messages_assigned_has_project` (0021:131); `email_drafts.project_id`
  and `email_draft_items.record_id` are RESTRICT; the remaining cascades
  depend on RI trigger order, which `db/restore.mjs` can reorder. There is no
  deletion path, and the schema resists adding one. `qa-clean` never deletes
  `email_messages`, so its sweep fails on any `__QA` project that received
  fake mail. Fix: cascade or clear-with-trigger on the three FKs; NO ACTION in
  place of order-sensitive RESTRICTs.
- **B6 (M, plausible). Lock-order inversion** between `answer-edit.ts:103`
  (answer, then record in `snapshotRecords`) and `confirm-drawings.ts:653`
  (records, then answers). A deadlock reaches the user as "someone else was
  changing this". `editCommonSpec` vs `correctAttribute` has the same shape.
- **B7 (M, plausible). The requirements seed is keyed by position**
  (`(category_id, sort_order)` upsert in 0003, 0007, 0009). Inserting one
  question into a revised cheat sheet rewrites the prompt of the row at that
  position and every answer on it changes meaning silently. Fix: a stable seed
  key, and a pre-check refusing to change a row that has answers.
- **B8 (M, plausible).** The same email uploaded twice is read twice:
  `email-ingest.ts:123` never looks at `internet_message_id` (indexed, never
  read) and `mime_sha256` is never written.
- **B9 (L).** Global correlated scans of `change_sets` by
  `evidence_attachment_id` per attribute and per finish row, no index
  (`records/[id]/route.ts:93`, `finishes/route.ts:36`). Retiring a finish races
  with linking. `qa-clean` uses `like '__QA%'` where `_` is a wildcard. Open
  changes never expire. Sent drafts, `notes` and `baseline_members` are
  protected against update only. The disagreement one-open-row index is void
  when `source_run_id` is null. `run-migrations.mjs` writes the ledger outside
  the file's transaction with no advisory lock. `restore.mjs` runs without
  `--single-transaction`. `backup.mjs` puts the password on the `pg_dump`
  command line. The 0013 layout seed upserts on `name` and can take over a
  person's layout. `backfill-finishes.ts` predates the twin lookup. No index
  on `spec_answers(requirement_id)`.
- **Dead or unread:** `users.last_login`, `email_messages.body_truncated`,
  `email_messages.mime_sha256`, `email_messages_internet_id_idx`; tables
  `messages` (0001), `notes`; plus the known `pick_lists`, `status_history`,
  `required_at_gate`, `tracking_eligible`.
- **Vocabulary guard gap:** twelve controlled vocabularies are not covered by
  `tests/db/vocabulary-sync.test.ts` (intake statuses and source kinds, record,
  run, attribute, note, project, draft statuses, attribute states, contact
  roles, gate value types, the tier). All match today.

### C. The bill intake pipeline

Clean: the header pair rule, layout exactness, `needsColumns` and the model
check gates, reconcile's one-to-one / SX11A handling, the run lock and record
numbering, `feetAndInches` (conservative, no false read found),
`composeDimensionCell`'s duplicate-slot / Dia-conflict / note-only / zero /
negative handling, the never-from-magnitude unit rule.

- **C1 (H, confirmed, two auditors). A revision retires every configuration.**
  `confirm-boq.ts:699-712` retires every active record on `replacesRunId` not
  in `carriedForward`; the loader at `imports/[id]/route.ts:1064-1085` has no
  `parent_id` filter; a configuration has no `boq_code`. The review lists them
  under "would be retired" with no control to keep them. Fix: a configuration
  follows its parent — exclude `parent_id is not null` from both, retire only
  with the parent.
- **C2 (H, confirmed). Two sheets pointed at one phase retire each other.**
  Nothing refuses two sheets with the same `replacesRunId`
  (`confirm-boq.ts:308-330`, PATCH at `route.ts:1339`); sheet 2's retire step
  sweeps sheet 1's new records. Fix: refuse a duplicate in both.
- **C3 (H, confirmed). `quantity()`** (`boq-import.ts:661-665`): `Number("")`
  is 0, so words become 0 and the "bill gave none" sentence never fires;
  stripping non-digits joins `2 x 3` to 23; a float or an out-of-range value
  reaches `spec_records.qty integer` (0002:195) and fails the whole confirm
  with a generic 500. The PDF path's `Number(cell)` has the float half. Fix:
  accept only `^\d[\d,]*(\.\d+)?\s*(nr|no\.?|pcs?|ea|units?)?$`, whole and in
  range; everything else null with the cell kept verbatim and flagged.
- **C4 (H, confirmed). A thousands comma reads as a decimal point.**
  `dimensions.ts:257` (`Number(stripped.replace(",", "."))`), also
  `spec-dimensions.ts` `splitFigure`/`figureWithUnit`. `1,200` → 1.2 → `W1mm`;
  on an unmarked drawing page `1,800` votes centimetres and lands as 18 mm.
  No test covers it. Fix: `\d{1,3}[.,]\d{3}` is ambiguous — refuse into the
  `not_numeric` bracket; a decimal comma only with one or two digits after.
- **C5 (H, confirmed). A revision adding a second finish of one kind refuses
  the whole bill.** `writeFabricLine` (`confirm-boq.ts` ~960-975) re-reads the
  held list per target, including rows it wrote earlier in the same confirm, so
  the second COM line finds the first held and throws `fabric_changed`; the
  review's `planBillFabrics` never adds what it plans to `heldFabric` and shows
  "→ COM 2". The `proposalBlockers` single-decision rule, broken. Fix: one
  pure planner feeding both; refuse only where a finish the record held BEFORE
  this confirm is missing from the revised lines.
- **C6 (M, confirmed).** The synonyms `item` and `ref` win by column order and
  the loser vanishes: `Item | Code | Description | Qty` names every record
  "1.01" and drops Description, with no columns check. Fix: two columns
  claiming one role marks the sheet as needing a look.
- **C7 (M, confirmed).** A narrow saved layout outranks the synonyms on every
  other bill and drops the code column; the confirm waits only for a MODEL's
  reading, not a person's layout. Fix: a layout applies only when it maps at
  least as many known headings as the synonyms would, or the confirm also
  waits on `columnsAwaitingALook`.
- **C8 (M, confirmed).** The bracket rule reads `CH-02 (CH-01)` ("as CH-01")
  as a fabric for CH-01, unflagged; `CH-01 (TO BE CONFIRMED)` as a fabric with
  no item. Fix: unflagged only where the line also looks like a finish.
- **C9 (M, confirmed).** A header row reprinted above each section becomes a
  record named "Description". Fix: skip and count a row whose mapped cells fold
  to the headings.
- **C10 (M, confirmed).** PDF bill rows anchor only on a numeric QUANTITY cell;
  a `TBC`/`-`/blank quantity merges the line into its neighbour, a description
  longer than four lines loses lines, a continuation page's title lands in row
  1, none flagged (`pdf-bill.ts` `pageRows`). The 575/575 measurement was on
  bills where every line had a number. Fix: anchor on code/description too;
  flag a cell holding text from two bands; cut above and below the table.
- **C11 (M, confirmed; wording plausible).** `fabricLineIsPlaceholder` misses
  "to be selected by client" / "by others", so one in-house finish is minted
  and every later line with the same words links to it: the merge the rule
  exists to prevent. Fix: `deferredToSomebody` phrases count as placeholder.
- **C12 (M, confirmed).** `Ø`/`⌀` never reach `normaliseDimensionSlot`
  (`parseCombinedDimensions` prefix class is `[A-Za-z.]`): `Ø600 x H750mm`
  places H only.
- **C13 (M, plausible).** A numeric cell is read raw, not as displayed: `1.10`
  reads "1.1" and collides with `1.1`; `0012` becomes "12".
- **C14 (M, confirmed).** A record retired by Rev B whose code returns in Rev C
  becomes a NEW record; the old one keeps its drawings, retired, and nothing
  offers "restore".
- **C15 (L).** Two lines can be paired to one record at PATCH; the confirm's
  `version` is optional; a second `normaliseRef` in `boq-import.ts:1521` writes
  `ref_value_norm` with a fold that differs from `record-refs`; the aggressive
  fold makes `CH-01.1`, `CH-011` and `CH-1.1` one key in `boq-carry` and
  `finishLineTargets`; `TRANSCRIPTION_CLAIM_MS` equals `maxDuration` rather
  than exceeding it; the transcribe route has no server-side single-try guard;
  no idempotency on bill registration (a double submit makes two runs); mock-up
  copies carry no `qty_unit`; the revision dropdown offers the mock-up phase;
  `code_not_in_text` is a substring test; `parseCombinedDimensions` splits on
  any `x` (`1200 max x 600`).

**Measured:** `confirmBoqImport` ~587 lines, the GET in `imports/[id]` ~386,
`planBillDescription` ~354, `patchDrawing` ~339, `patchBoqLine` ~295; the route
file is 2,196 lines carrying bill, drawing and proposal halves. Six
number-from-text readers with different rules (C3, C4 come from that). Two
`normaliseRef`s and four other fold helpers.

### D. The model-read and drawings pipeline

Clean: every worker write is fenced on run + attempt + token + status and zero
rows is "skipped"; the slot advisory lock is taken before the row lock
consistently; no import cycle among the 184 lib files (a Tarjan pass); the
unit order is printed → page vote → default → nothing as designed;
`normaliseDimensionSlot` is whole-label; model output is never a path, key or
HTML; all four `assertStagedDrawings` callers pass palettes.

- **D1 (H, confirmed). A timed-out read costs up to four reads.**
  `anthropic.ts:768` sets the deadline; nothing checks `signal.aborted`, so
  the SDK's abort error lands in the last branch of
  `classifyTransportFailure` (`:920-922`) as retryable `transport`, and
  `extraction-run.ts:217` re-queues it. A 100-page set (only WARNED at 70)
  runs ~740 s, aborts, and is redelivered four times, each billed for the
  tokens streamed before the abort, then fails with "could not be reached".
  Fix: a deadline or abort is terminal (`timeout`, "split the document"), as
  `document-classify.ts:209` already does.
- **D2 (H, confirmed). A stale replace tick retires a value into a note.**
  `acknowledgedReplacements` is keyed on the record; `confirm-drawings.ts:986`
  calls `retireOccupant(…, slot = null)`; the ordinary PATCH keeps `replaces`

## 3. The patterns under the findings

Seven things recur; each explains several entries above, and the plan in §5
fixes them as patterns rather than one entry at a time.

1. **Provenance is inferred, not recorded** (E1, E5, B1, E6). An answer's
   origin is guessed from `document_kind`; a version's membership from a
   conflict clause; a correction's lineage from a pointer four of five paths
   set. Each inference was right when written and wrong one feature later.
2. **The screen and the write boundary decide the same thing twice** (C5, D2,
   D3, G1). CLAUDE.md's rule is one function for both; `planBillFabrics` vs
   `writeFabricLine`, the replace tick vs `retireOccupant`, and the versions a
   click sends vs the ones the save chain produced are three places it has
   slipped.
3. **A number is read six ways** (C3, C4, D10). Six readers, each with its own
   rule for commas, words and fractions. One `readPrintedNumber` with named
   outcomes (whole / decimal / ambiguous-comma / words / none) and one test
   file closes three findings.
4. **The configuration is a second-class record** (C1, D5, F14's email order,
   the three heading-predicate omissions). It has no bill code, sorts under
   its parent only where someone remembered, and is swept by anything keyed on
   the phase.
5. **A guard written for one shape is applied to another** (B1's conflict
   clause, D9's 360 s literal, C15's `TRANSCRIPTION_CLAIM_MS`, D8's retry
   backoff against a thrown busy). Timing and uniqueness constants should be
   imported, never retyped, and the timing test should cover every route that
   declares a `maxDuration`.
6. **The write boundary is not the authorisation boundary** (A4, A13, H3).
   Role lives in a seven-day token read only by a prefix-matching matcher;
   nothing in a handler asks it; no test asserts it.
7. **What the tests prove and what CI runs are different sets** (H1–H4). The
   db tier is where every confirm lives, and it runs only when a person on
   this machine remembers.

  not reproduced on a screen; a few will turn out to be guarded by something
  the tracing missed, and the first task of each fix is to write the failing

  re-found a known item it is listed under "Already known" in that report and
  omitted here. The reports themselves are in this session's transcript and
  not in the repo.

  matters, so a short low list in one area means the auditor stopped, not that
  the area is clean.

  attribute, the 300-line loaders) are to be taken on the local stack's copies
